01Requirements

  • OpenChamber 2.8.0 or newer. The manifest declares engines.openchamber: ">=2.8.0"; the tracker contract and the SDK version it targets do not exist in older builds.
  • A Jira Cloud site. A *.atlassian.net site or a custom domain that reports deploymentType: "Cloud" from /rest/api/3/serverInfo. Jira Server and Data Center are refused.
  • A licensed Jira user who can browse the projects you want to see. The token acts as that user.
  • Permission to install a local extension in OpenChamber (a folder or a ZIP).
No extra server

The extension is a local service started by OpenChamber. You do not run a daemon, create a database, or expose a port. It reaches Jira only through OpenChamber's outbound proxy.

02Install

There are two tested paths: a ZIP from the latest release, or a folder from a checkout.

From the ZIP (recommended)

  1. Download openchamber-jira.zip.
  2. Open Settings → Extensions in OpenChamber.
  3. Paste the absolute path of the ZIP into Folder, ZIP, or URL and choose Add.
  4. Approve the extension when OpenChamber asks. It asks to run a local service (the tracker service) and to connect to an external service (Jira).

A ZIP is copied into OpenChamber's data folder. Updating means adding the new ZIP; OpenChamber treats it as a new version of the same extension.

From a checkout

git clone https://github.com/pgquiles/openchamber-jira

Add the absolute path of the openchamber-jira folder in Settings → Extensions, the same way as a ZIP. No build is needed: the repository ships the runtime entry service/main.js, and OpenChamber runs it as-is. A folder install picks up changes when you reload the extension.

The npm scripts are for development: running the tests, rebuilding after a change to service/*.ts, and packaging the release ZIP.

What gets installed

FilePurpose
package.jsonManifest: panel, service, tracker contribution, engines

There is no build step at install time and no runtime dependency to fetch. If you change service/*.ts, rebuild: OpenChamber does not run the TypeScript sources.

03Connect a Jira site

  1. Create an API token at id.atlassian.com → Security → Create and manage API tokens. A classic token is simplest; a scoped token needs the scopes in Permissions.
  2. In OpenChamber, open Settings → Integrations → Extension accounts and find the Jira card.
  3. Fill in:
    • Jira site — https://your-company.atlassian.net. No path, no trailing slash. A custom domain is fine if it serves the Jira REST API.
    • Username — your Atlassian account email. OpenChamber labels this field neutrally for Basic auth; Jira calls it the user name.
    • Token — the API token from step 1.
  4. Choose Connect.

The extension checks /rest/api/3/serverInfo first and refuses non-Cloud deployments, then identifies the account through /rest/api/3/myself, and finally asks for one project the account can browse. An account that can see no project is refused at connect, with the fix, instead of being connected to a board that stays empty. A private site that redirects an unauthenticated request to its sign-in page is still recognized as Jira Cloud.

When the card says Connected, you can turn on Project mapping and Session comments if you want those OpenChamber features.

The token is stored by OpenChamber

The extension's service never receives the token. OpenChamber adds the Authorization: Basic … header in its outbound proxy and pins requests to the site you entered.

403The account or token lacks the permission for that project, or Jira denied the call. If connect says the account cannot browse any project, add it to one (or check the token scopes) and connect again.
404The issue or project moved or was deleted, or this account cannot see it. Check the key in Jira and the account's project access.

04Permissions and scopes

The token acts as your Jira user. OpenChamber can never show an issue that user cannot see in Jira.

FeatureJira permission
Find issues, read details, projects, and statusesBrowse projects
Change an issue's stateTransition issues
Post session commentsAdd comments

Connecting needs Browse projects somewhere on the site. A read-only token connects: Transition issues and Add comments are checked by the action that needs them, so only that action fails, with a message naming the missing permission or scope.

Scoped API tokens

If your organization requires scoped tokens, grant:

  • read:jira-work — search, issues, projects, statuses
  • write:jira-work — transitions and comments
  • read:jira-user — identifying the account with /myself

A classic token works too, with the user's full Jira access. The extension does not ask for Atlassian administration scopes and cannot read users it does not need.

05SSO and organization policy

This extension uses HTTP Basic authentication: your Atlassian account email plus an API token. SSO does not block this. Atlassian API tokens authenticate even when the organization enforces SAML single sign-on or two-step verification, and Atlassian does not ask for an extra identity check when an SSO user creates a token.

What an organization can still change:

  • API token policy. An organization admin can block members from creating or using user API tokens, or cap their lifetime, through an Atlassian Guard authentication policy. When that is on, Jira answers 401/403 and the extension cannot override it. The account needs an exception, a service account, or OAuth.
  • Expiry and revocation. New tokens expire after one year by default, and admins can revoke them earlier. After a revocation Jira's search answers with an empty result rather than 401, so a board that stops listing issues is the usual symptom; create a new token and reconnect.
  • Scopes. A scoped token needs read:jira-work, write:jira-work, and read:jira-user. A classic token works too, with the user's full access.
  • Product access. The account must still be a licensed Jira user with permission to browse the projects.
Before a company rollout

Atlassian's current guidance discourages integrations that collect and store personal API tokens. Check whether your organization blocks them. If it does, use an organization-approved service account as the interim path; OAuth 2.0 3LO is the durable replacement.

Why OAuth is not a one-line change

Jira's 3LO access tokens are sent to https://api.atlassian.com/ex/jira/{cloudId}, not directly to the site origin. OpenChamber's tracker host pins outbound proxy requests to the instance origin, and the extension also needs the cloud id from /oauth/token/accessible-resources. Supporting OAuth therefore needs an upstream way to declare an API origin (or resolve the cloud id) in addition to the manifest's auth.oauth block. It is tracked in issue #1.

What a service account changes

A service account is a normal Jira user with its own token and the permissions above. It survives employee turnover, can be scoped to the projects that matter, and is easier to justify to an organization than a personal token. The trade-off is that comments and changes appear as the service account, not as the person who made them. Decide that with your team before rolling it out.

06Where Jira appears

OpenChamber 2.8.0 draws the tracker UI itself. The extension does not add a separate Jira rail panel, and the Jira card in Settings holds only the connection and its optional mapping. The issue list is the Jira tab on the issues board; the picker is a composer action.

What “rail panel” means (and why there is not one)

OpenChamber's right rail is the strip of panel icons beside the chat: Git, Files, Terminal, and any extension that ships a panel page. An extension gets one by pointing contributes.panel.entry at an HTML page. This extension's panel has no entry, so no Jira icon or Jira panel appears there. The tracker contract itself only draws the board tab, the composer picker, and the detail view.

A Jira rail panel would be an extra view — for example, a list of issues assigned to you that opens from a Jira icon. The idea, with a sketch, is tracked in issue #16. It is not in 0.3.2: a guest page cannot read tracker items today, because the tracker API is host-side and the credential and session handle stay in OpenChamber. It waits on an upstream guest read path or a host-drawn panel.

Status and comments

Open the issue from the issues board. The composer picker's preview is for choosing an issue and stays read-only; the board's detail (side preview or issue tab) has the state menu. Click the state pill in the header to move the issue. The extension resolves the issue's available transition and sends only the destination; a transition screen that needs fields fails with Jira's own 400 error, which names the missing fields (a custom field by display name and id; see States and transitions).

Comments are shown but not writable in OpenChamber 2.8.0. The tracker contract's comments.create is used only by the optional session comments, which post a summary when a session starts, finishes, or fails. A user comment box for tracker items is a host gap, tracked in openchamber#7641.

Long project lists

The board's project picker is also drawn by OpenChamber. In 2.8.0 it has no scrollbar on a site with hundreds of Jira projects, so projects after the first screenful cannot be reached. That is a host bug, already fixed on main by #7430; 2.8.0 is the only affected release, tracked here as issue #15. Until the next release, use the composer's picker, which has its own project filter and search.

07Find and link an issue

Open the composer's + menu and choose Link Jira Issue. The @ menu is for file mentions, not Jira. The same issue list is the Jira tab on the issues board. The default view is open issues you can see, most recently updated first. Choose Assigned to me to narrow it to your queue; search matches issue keys and summaries.

FilterBehaviour
People · Assigned to meassignee = currentUser()
People · Created by mereporter = currentUser()
People · AnyoneNo people clause; still limited by Jira's project permissions
Stateopen, all, todo, in-progress, done mapped to Jira status categories
PriorityThe site's own priority names; none means an empty priority field
ProjectProjects act as containers, keyed by project key so the id works in JQL

The picker reads up to 100 issues per page. More pages are available through Jira's next page token. The priority list is cached per site for five minutes.

Linking an issue adds it to the session's linked items. It does not move the issue, assign it, or write anything to Jira.

08Read an issue

The issue panel shows the summary, status, assignee, priority, project, and labels, plus:

  • Description — converted from Atlassian Document Format to Markdown. Paragraphs, headings, lists, code blocks, tables, links, mentions, inline cards, media and attachments as links, panel tones, expando titles, and status lozenges are handled. An ADF node the converter does not know appears as [nodeType] instead of disappearing.
  • Comments — up to 100, read-only in the detail view (see Comments). With the newest kept if the response budget is exceeded; when even those do not fit, the oldest comments are dropped.
  • Parent and children — native sub-tasks and parent, team-managed epic children, and company-managed Epic Link children. The Epic Link field is discovered by its custom-field schema, so localized field names still work.
  • Done / total — a count for the child issues Jira returns, with a marker when Jira truncates the list.

09States and transitions

OpenChamber's tracker contract uses four states. Jira reports a status category; the extension maps it like this:

Jira status categoryOpenChamber state
newtodo
indeterminatein-progress
donedone
canceled or duplicate status namedone — Jira has no native canceled category
Missing or unknownnull — never guessed

To change state, the extension reads the issue's available transitions and picks the one whose destination is the status you chose. It does not invent a transition or fall back to a different status.

Workflow screens

Some transitions require a screen with fields — resolution, a comment, a custom field. The tracker contract sends only the destination, so the extension cannot complete that step. Jira's own 400 is shown instead of guessing values; it names the missing fields, using a custom field's display name and keeping its id. The issue header links to Jira, where the transition can be finished. Rendering the screen needs the contract to accept transition fields.

10Comments

The detail view shows an issue's comments read-only. OpenChamber 2.8.0 draws no comment composer for tracker items, so this extension cannot add one from the tracker contract. Tracked upstream in openchamber#7641.

Session comments are posted as valid Atlassian Document Format, with the session link kept as a link mark. You need the Add comments permission on the issue's project.

This is the only write besides a state change. The extension does not edit descriptions, delete comments, attach files, or change assignees.

11The account card

Settings → Integrations → Extension accounts holds the connection. The connected card shows the Jira account and site, with Connect / Disconnect, and exposes the optional OpenChamber settings. It is not the issue list; that is the Jira tab on the issues board, or the composer picker.

The card also offers Add account, and the board's account picker switches between connected accounts. The new account is verified against the same Jira site, so this covers a shared workstation or a personal account plus a service account. A second Jira site is not possible in OpenChamber 2.8.0: the host stores one instance per tracker and hides the site field once an account exists. A credential for another site is checked against the connected one — 401 if the user is not a member there, an account on the wrong site if they are. This needs a host change (openchamber#7653), tracked as #9.

  • Project mapping — choose a default Jira project and how OpenChamber containers map to Jira projects.
  • Session comments — allow posting a session summary as a Jira comment.

Collecting details for a report

Open an issue with the OpenChamber version, the extension version, the Jira deployment type (Cloud), the failing action, the HTTP status, and Jira's error text. Do not paste an API token. Redact site names and issue keys if they are sensitive.

13Security and privacy

  • Token handling. OpenChamber stores the API token and adds the authorization header in its outbound proxy. The extension service receives request handles, not the token.
  • Network scope. Requests go only to the Jira site you entered, through the proxy. The extension makes no analytics, telemetry, or third-party calls.
  • Least privilege. Reads are GETs. The only writes are the state transition and the session comment you explicitly request.
  • Visibility. Everything Jira returns is filtered by the token's permissions. The extension has no separate cache or database.
  • Source. The extension is MIT licensed and the service is a single readable bundle built from service/*.ts. You can audit it before installing.
A personal token is still personal

A user API token can read everything its owner can read. Treat it like a password: do not share it, do not commit it, and revoke it when it is no longer needed.

15Development

npm install
npm run typecheck   # tsc
npm test            # rebuild the bundle, then bun test
npm run build       # bundle service/main.ts → service/main.js
npm run check       # openchamber-guest-check .
npm run verify      # all of the above
npm run zip         # openchamber-jira.zip
PathPurpose
package.jsonExtension manifest and scripts
service/main.tsTracker service: handlers, Jira calls, HTTP server
service/jira.tsStatus/priority mapping, JQL, key checks, Epic Link helpers
service/adf.tsAtlassian Document Format ↔ Markdown
service/main.jsBuilt bundle; the file OpenChamber runs
test/fixtures/fake-jira.tsJira Cloud stand-in for contract tests
test/service.test.tsEnd-to-end tests through a proxy that enforces the contract
test/adf.test.ts, test/jira.test.tsUnit tests

The contract tests spawn the built service/main.js, send POST /tracker requests with the service bearer, and play OpenChamber's outbound proxy in front of a fake Jira. Read requests go through GET-only handles; writes use POST. That is how the tests catch a method the real host would refuse.

Rebuild after changing service/*.ts. The repository's npm test rebuilds first through the pretest script, so a stale bundle cannot make the tests pass.

CI runs typecheck, tests, guest check, the bundle check, and the ZIP build on every pull request and push to main. It fails when the checked-in service/main.js is stale. A v* tag runs the release workflow and publishes a GitHub Release with openchamber-jira.zip attached. The verify check is required to merge into main.

Contributing

Open an issue before a substantial change so the contract implications are clear. Run npm run verify before a pull request, and include a test for the behaviour you changed. The site lives in site/ and deploys to GitHub Pages on every push to main that touches it.

16Roadmap

The queue, in the order that unlocks the most:

  1. OAuth 2.0 3LO for organizations that block personal API tokens (#1).
  2. Create and edit issues — needs the tracker contract to grow (#2, upstream openchamber#7647).
  3. Token health — expiry, scopes, and a clear needs-attention state (#3).
